# 🔭 Vantage: Spec for Audio-Rate Pattern Control of Voice Parameters

👤 **User Story:** "As a Sound Designer and Live Coder, I want to control synthesis voice parameters (like filter cutoff or FM index) at exact audio rates driven by language patterns, so that I can create complex, sample-accurate, and dynamically modulating timbres beyond simple breakpoint interpolation."

**The "So What?" (Business Problem)**
Currently, voice parameter automation (`p1`..`p4`) interpolates linearly between up to 32 breakpoints per note. While efficient, this acts essentially as a low-frequency LFO or stepped envelope. It is insufficient for high-speed synthesis techniques like audio-rate FM, AM, or true audio-rate filter sweeps. If a user tries to pattern a fast modulation, it gets smoothed out or bottlenecked by the breakpoint limit. Complexity is a cost; utility is a revenue. Enabling pattern-driven signals to act as true audio-rate streams at the engine level dramatically expands Orpheus's sonic territory, positioning it as a capable modern synthesis engine rather than just a sequencer of static or slowly-evolving voices.

**Metric Definition**
- **Success** = Users can define an audio-rate signal (e.g., a fast sine wave) in a pattern and map it to a voice parameter (`p1`..`p4`), with the engine rendering the modulation accurately at the audio sample rate without glitching, stepping, or dropping below a real-time buffer processing speed (e.g., maintaining < 5ms render time per block).

**Gap Analysis**
- **Current State (Orpheus):** Parameters (`p1`..`p4`) are limited to breakpoint-rate (up to 32 points per note) and are linearly interpolated per-frame.
- **Competitors (TidalCycles, Faust):** Tidal patterns mostly sequence events. Systems like Faust blur the line between control and audio rate seamlessly.
- **The Gap:** Orpheus lacks the ability to transmit continuously evaluated pattern data into the DSP graph at the audio sampling rate.

✅ **Acceptance Criteria:**
- Must introduce a mechanism to evaluate specific pattern controls as continuous audio-rate signals rather than discrete note breakpoints.
- Must pipe these audio-rate control streams directly into the voice parameters during block rendering.
- Must execute the DSP graph such that the parameter modulates smoothly per sample, not per block or breakpoint frame.
- Must ensure that literal, un-optimized audio-rate pattern evaluation does not block the real-time audio thread (e.g., by utilizing an audio-rate signal buffer or DSP-side oscillator primitive generated by the pattern, rather than literally evaluating language syntax per sample).

🚫 **Out of Scope:** Literal pattern evaluation at the audio rate (as explicitly stated in the roadmap). The solution must map pattern definitions to DSP-level audio-rate signal generators/buffers, not evaluate the language AST millions of times per second.
