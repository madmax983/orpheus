# 🔭 Vantage: Spec for MIDI Output Support

## 👤 User Story
"As a Live Coder, I want to send MIDI note and control change messages from Orpheus to external hardware synthesizers or other DAWs, so that I can sequence external analog gear or complex software instruments using Orpheus's pattern language instead of being limited solely to the built-in DSP engine."

## ❓ The "So What?" (Business Problem)
Currently, Orpheus is a closed ecosystem. While the internal DSP engine and sample bank are powerful, many electronic musicians have extensive setups involving external hardware synthesizers, modular gear, or specialized software instruments in DAWs like Ableton Live or Logic Pro. By lacking MIDI output, Orpheus forces users to choose between the expressiveness of its pattern language and the sound design capabilities of their existing gear. Complexity is a cost, and utility is revenue: adding MIDI output acts as a massive utility multiplier by turning Orpheus into a central brain/sequencer for an entire studio, drastically expanding its appeal to producers who already own hardware. It bridges the gap between terminal-based composition and tangible, external sound generation.

## 🎯 Definition of Success
- **Success** = Orpheus can discover available system MIDI output ports, connect to a user-specified port via a REPL command, and transmit sequenced note events (Note On/Off) generated by `Pattern<Note>` bindings with <5ms of jitter relative to the internal audio clock, without causing any blocking or allocation on the real-time audio thread.

## 🔍 Gap Analysis
- **Current State (Orpheus):** Audio generation is strictly internal via the custom DSP engine and sample playback. No communication with the outside world.
- **Competitors (TidalCycles, Strudel):** Both have robust MIDI integration. TidalCycles often sequences external gear via SuperDirt MIDI outs. Strudel can send WebMIDI.
- **The Gap:** Orpheus needs a dedicated, low-latency MIDI output layer that translates its internal exact-rational cycle timing into timestamped MIDI messages sent to the OS MIDI scheduler.

## ✅ Acceptance Criteria
- Must introduce a command in the REPL/TUI (e.g., `:midi list`) to list available system MIDI output ports.
- Must introduce a command (e.g., `:midi connect "Port Name"`) to open a connection to a specific MIDI destination.
- Must support a new `midi("channel")` destination in the language (or similar syntax) to route a pattern to the external MIDI port rather than the internal audio bus.
- Must translate Orpheus note events (which have a start time and duration) into explicit MIDI Note On and Note Off messages.
- Must handle overlapping notes and chord generation correctly.
- Must execute MIDI transmission on a dedicated high-priority background thread (or via the OS MIDI scheduler queue) to ensure zero locks, allocations, or blocking on the real-time audio generation thread.

## 🚫 Out of Scope
- MIDI Input (e.g., playing Orpheus synths with an external MIDI keyboard). Phase 1 is strictly sequencing *out*.
- MIDI Clock Sync / MTC (sending or receiving). We are sending note data only; external gear must act as a sound module, not a sequenced clock follower for Phase 1.
- Polyphonic Aftertouch or complex MPE (MIDI Polyphonic Expression) routing.
- Loading external VST/AU plugins directly inside Orpheus. MIDI is sent out to the OS, which routes it to standalone apps or DAWs.
