# 🔭 Vantage: Spec for Tracker-Style Visualization

## 👤 User Story
"As a Composer, I want to see my code-based musical patterns rendered as a visual grid (like a traditional tracker), so that I can easily verify the timing, note alignment, and rhythmic structure across multiple layers without having to mentally parse the code."

## ❓ The "So What?" (Business Problem)
Code-based music programming is powerful for generative and structural composition, but it suffers from a major accessibility and verification problem: it is inherently difficult to visualize complex polyrhythms and overlapping sequences just by reading text. This leads to friction where the composer must play the pattern to understand it, slowing down the creative iteration loop. A tracker-style visualization bridges the gap between text-based live coding and traditional grid-based sequencing. By providing a read-only, real-time visual cross-check, we reduce cognitive load, making the platform more approachable for musicians transitioning from DAWs or traditional trackers like Renoise, and speeding up the debugging process for complex patterns. Complexity is a cost; utility is revenue.

## 🎯 Metric Definition
- **Success** = The visualization accurately reflects the active patterns in real-time, rendering a scrolling or paginated grid where rows are time steps and columns are musical layers. The update latency from code evaluation to visual update must be < 50ms, ensuring immediate visual feedback.

## 🔍 Gap Analysis
- **Current State (Orpheus):** The interface is primarily a REPL and text editor. Users must rely entirely on their auditory feedback or mental modeling to understand the timing and alignment of their coded patterns.
- **Competitors (Renoise, TidalCycles, Strudel):** Renoise is entirely built around the tracker paradigm. Strudel offers some visual piano roll/grid feedback. TidalCycles relies on external visualizers.
- **The Gap:** Orpheus lacks a built-in visual representation of the scheduled events generated by the pattern engine, making it harder to debug complex rhythmic interactions.

## ✅ Acceptance Criteria
- Must introduce a new visual pane or overlay in the TUI representing a tracker-style grid.
- Rows must represent discrete time steps (e.g., subdivisions of the cycle).
- Columns must represent distinct musical layers or active patterns.
- The grid must populate automatically based on the currently evaluated and active patterns.
- The grid must visually indicate the current playback position (playhead).
- The grid must be read-only; it is a visualization of the code, not an alternative input method.
- Performance must not degrade significantly; the grid rendering must not cause audio stuttering.

## 🚫 Out of Scope
- Interactive editing via the tracker grid (this feature is strictly for visualization; editing remains code-first).
- Deep inspection of DSP parameters per note in the grid (Phase 2).
